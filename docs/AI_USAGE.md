# AI 코딩 보조 도구 사용 내역

## 쓴 도구

지원자는 Claude Code(모델 Claude Opus 5.5)를 Orca 터미널에서 실행했습니다. Claude Code 안에서 웹 조사용 하위 에이전트, 코드 리뷰용 하위 에이전트, Orca 내장 브라우저 자동화, AWS CLI, Docker, uv를 함께 썼습니다.

## 왜 썼나

과제는 11월 16일에 시작해 11월 18일 18시에 마감했습니다. 그 안에 설계 논의, 구현, 화면 확인, AWS 배포, 문서를 모두 끝내야 했습니다. 지원자는 조사, 마크업, 스크립트, 반복 확인을 AI에 맡겼습니다. 대신 요구사항 해석과 결과 검토에 시간을 썼습니다.

## 단계별 사용

| 단계 | AI가 한 일 | 지원자가 한 일 |
|---|---|---|
| 요구사항 정리 | 과제 문구에서 정해야 할 결정을 질문으로 뽑아 라운드마다 추천안과 함께 제시함. 구현 전에 4라운드 25문항, 제출 준비와 관리 화면 재구성 때 3라운드 21문항을 물음 | 질문마다 답함. 이해가 안 되는 질문은 더 자세히 설명하게 함 |
| 회사·콘텐츠 조사 | 사람인 공고와 hero-school.net을 읽고 기술 스택, 사업 구조(학교로 찾아가는 B2B 수업), 과정별 커리큘럼 원문을 정리함 | 어떤 과정을 쓸지 고름 |
| 구현 | Django 모델, API, 페이지, SCSS, JS, 메일과 시트 기능, 테스트를 작성함 | 화면 문구와 동작을 검토함 |
| 확인 | Django 테스트를 돌림. 내장 브라우저로 데스크톱과 모바일(390px) 화면, 신청, 우편번호 검색, 관리 화면 동작을 확인함 | 결과를 확인함 |
| 배포 | AWS CLI로 EC2와 RDS를 만들고 Docker 배포, cron 등록, 운영 서버 점검을 함 | 비용이 드는 실제 배포를 할지 정함. Gmail 앱 비밀번호와 Google 서비스 계정 키를 만들어 전달함 |
| 문서 | README, AWS 구성, 용어집(CONTEXT.md), ADR 초안을 씀 | 내용을 검토함 |
| 문장 정리 | 코드 주석, 화면·메일 문구, 문서에서 AI 문체(대시, 화살표, 연결어미 뒤 쉼표, 섞인 존댓말)를 고침. 문자열을 가린 Python AST, 주석과 문자열을 가린 JS, 컴파일된 CSS를 고치기 전과 비교해 코드 동작이 그대로인지 확인함 | 정리를 요청하고 결과를 검토함 |
| 관리 화면 재구성 | Django admin에 맡기던 신청 CRUD와 교육 편집을 전용 관리 화면으로 옮김. 별도 하위 에이전트에게 변경분 리뷰를 맡김 | Django admin 대신 전용 화면을 만들기로 정함. 구현할 때 도메인을 데이터 구조로 표현하라는 원칙을 지정함 |

## 지원자의 결정과 AI 추천이 달랐던 곳

AI는 질문마다 추천안을 냈고 지원자는 대부분 받아들였습니다. 아래 결정은 추천과 다르게 정했습니다.

| 질문 | AI 추천 | 지원자 결정 | 이유 |
|---|---|---|---|
| 우대 과제 범위 | 시트 내보내기는 시간이 남으면 | 우대 과제 4개 모두 | 전부 해 보는 것이 목표 |
| AWS | 마감까지 3일이 안 남으면 문서만 | 실제 배포 | 리뷰어가 링크로 바로 확인할 수 있게 |
| 스타일 | 순수 CSS | SCSS | 회사 기술 스택(SCSS/Sass)에 맞춤 |
| 중복 신청 | 진행 중인 신청이 있으면 막기 | 받고 관리자에게 표시 | 담당자가 판단하도록 |
| 개인정보 동의 | 동의 시각까지 저장 | 체크박스만 | 실제 운영 전제가 아님 |
| 시트 내보내기 | 버튼으로 덮어쓰기 | 버튼과 매일 자동 덮어쓰기 | 영향을 설명받은 뒤 결정 |
| 관리 화면 범위 | 신청 CRUD만 새로 만들고 교육 편집은 Django admin에 둠 | 교육과 커리큘럼 편집까지 전용 화면 | Django admin 없이 모든 데이터를 관리하도록 |
| 이 문서의 화자 | 지원자 1인칭 | 3인칭 기록 | 지원자 선택 |

AI의 조사와 질문으로 처음 알게 되어 반영한 것도 있습니다.

- 히어로스쿨은 학교로 찾아가는 수업이 주력입니다. 그래서 신청자를 기관 담당자로 보고 주소를 수업 장소로 해석했습니다([ADR 0001](adr/0001-applicant-is-organization-staff.md)).
- 연락 가능 시간대를 받기로 하자 AI가 전화할 번호가 없다는 모순을 짚었습니다. 그래서 연락처 필드를 추가했습니다.

## AI가 틀렸다가 바로잡은 것

| 문제 | 원인 | 조치 |
|---|---|---|
| AWS EC2 생성 실패 | user-data 스크립트의 한글 주석을 Windows용 AWS CLI가 읽지 못함 | 주석을 영어로 바꿈. 이미 만든 보안 그룹과 RDS는 그대로 두고 나머지만 이어서 만듦. 잃어버린 DB 비밀번호는 재설정함 |
| 로컬 서버 500 오류 | `.env`의 빈 `DJANGO_SECRET_KEY=`가 기본값을 덮어씀 | 빈 값도 기본값으로 처리함 |
| 첫 화면 리다이렉트 | 잘라낸 쿼리셋에 `get_object_or_404`를 씀 | `first()`로 바꿈 |
| 콘솔 메일 출력 실패 | Windows 콘솔(cp949)이 en dash 문자를 출력하지 못함 (로컬에서만) | UTF-8 모드로 실행함. 이때 실패한 메일이 다음 실행에서 다시 나가는지도 확인함 |
| 메일 규칙이 폼 저장 코드에 흩어짐 | 처음 구현에서 날짜를 바꾸면 발송 기록을 지우는 코드를 폼과 Django admin 양쪽에 두었음. 확인 메일을 끄면 보내지 않은 메일에도 발송 시각을 적었음 | 지원자가 지정한 원칙에 따라 다시 설계함. 메일을 끈 선택은 별도 필드로 저장함. 안내 메일은 오늘 날짜로 된 발송 기록이 있는지로 판단하게 바꿈. 지우는 코드가 사라짐 |
| 테스트가 실제 Google 시트를 건드릴 뻔함 | 로컬 `.env`에 실제 시트 설정을 넣은 뒤에도 "설정 없음" 테스트가 환경변수를 그대로 읽음 | 그 테스트에서 설정을 비우도록 고정함 |

## 검증 원칙

- AI가 됐다고 한 기능은 테스트나 실제 화면과 응답으로 확인했습니다. 확인 방법은 README의 테스트 항목과 위 표에 적었습니다.
- 중요한 테스트는 고치기 전 코드로 되돌려 실제로 실패하는지도 확인했습니다. 예를 들어 연락 가능 날짜를 바꾼 뒤 안내 메일이 다시 나가는지 보는 테스트는, 옛 규칙에서는 `(0, 0) != (1, 0)`으로 실패합니다.
- 운영 비밀값(DB 비밀번호, `SECRET_KEY`, Gmail 앱 비밀번호, Google 서비스 계정 키)은 `secrets/`에만 두었고 저장소에는 넣지 않았습니다. 관리자 계정 비밀번호도 스크립트가 무작위로 만들었습니다. 다만 과제 확인용 데모라서 지원자가 README에 공개하기로 정했습니다.
